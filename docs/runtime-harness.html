runtime-harness

two of three inspectors verified in-game   SKSE plugins that hook under-instrumented engine subsystems and log their live internal state.

The problem

The Skyrim RE community has excellent static tooling (IDA, Ghidra, BinDiff) and excellent animation introspection (Open Animation Replacer). But the engine's AI scheduler, Havok physics step, and savegame serializer have zero purpose-built runtime visibility. Every finding about them today arrives as static RE embedded in patch code — nobody watches them run.

The solution

SKSE plugins that hook into those subsystems and log their internal state live, in real gameplay — not just what a disassembler can infer statically.

Status: builds, loads, and runs in-game

A real SKSE plugin (RuntimeHarness) builds against CommonLibSSE-NG, sets up file logging, and logs the plugin/game version plus kDataLoaded/kNewGame/ kPreLoadGame/kPostLoadGame from the messaging interface — confirmed running against a live Skyrim AE 1.6.1170 process (SKSE64 2.2.6).

AIProcessInspector verified in-game

Package evaluation and AI scheduler decisions. Hooks Actor::Update via vtable — on both RE::VTABLE_Actor and RE::VTABLE_Character, since live NPCs are Character instances with their own vtable. RuntimeHarness.log shows a dozen-plus live NPCs' package-evaluation transitions during a fresh game's opening scene, changing over time as expected.

HavokStepLogger open question

Collision/ragdoll state per physics step. Hooks bhkCharacterState::Update across all six concrete character-state vtables (OnGround/Jumping/InAir/Climbing/Flying/Swimming) and logs physics-state transitions with velocity magnitude. Not yet actor-attributed (keyed by hkpCharacterContext address, not a form ID). Deployed and installed cleanly in-game, but produced zero log output across 70+ minutes of real gameplay (Helgen intro through open-world Whiterun, including combat-adjacent NPC activity) — long enough to rule out timing. The vfunc index, input delivery, and a possible PlayerCharacter-specific hierarchy were all independently checked and ruled out. Checked real prior art: ersh1/Precision (GPL-3.0, the standard SKSE-community reference for Havok hooking) has zero references to bhkCharacterState or hkpCharacterState anywhere in its ~2,200-line hooking code — it hooks RE::bhkWorld's physics-step function directly via a mid-function Xbyak trampoline instead of vtable-hooking the state machine. No serious working plugin uses this project's approach. Scoped follow-on, not attempted: rebuild Precision-style, which needs Xbyak enabled in this project's build (currently off) plus a vcpkg dependency and re-verified offsets — a real feature task, not a quick fix.

SavegameTracer verified in-game

Hooks BGSSaveLoadManager::ProcessEvent via vtable — a genuine singleton, so exactly one concrete vtable. Dumps saveGameList (filename, player name, race, location, playtime) on every firing, since the actual event payload types are only ever forward-declared in the vendored tree. Confirmed firing live in-game: a real ProcessEvent call with a real saveGameList query (the list was empty at that moment, since no save existed yet in the session — itself correct live data, not a failure).

A further idea unlocked by the rest of this repo: a struct-layout validator that checks type-importer's generated layouts against the running game — stronger ground truth than static_asserts.

Why this builds against the vendored CommonLibSSE-NG

The plugin compiles against type-importer/vendor/CommonLibSSE-NG (v3.7.0) directly — the exact headers the .gdt type archives are generated from — so the runtime harness and the type archives can never disagree about a struct layout.

Platform: Windows-only, no exceptions

SKSE plugins are Windows DLLs built against Skyrim's Windows PE ABI — this piece cannot be built or tested on Linux the way type-importer can. Builds happen on a dedicated Windows machine (Visual Studio + SKSE64) driven over SSH from the rest of this project's Linux-native workflow.
