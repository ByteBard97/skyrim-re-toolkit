Known Limitations

Every honest caveat about this toolkit's current accuracy and coverage, gathered in one place instead of scattered across five READMEs and a dozen patch docs. Nothing here is new — it's all already documented elsewhere; this page just saves you the hunt.

type-importer — parser accuracy

Not every class is byte-accurate yet. Coverage is measured against coverage_baseline.json per runtime via scripts/check_regression.py — see type-importer for the current OK/checkable counts.
About the ~1,041 classes reported as "EMPTY" (resolved but 1 byte, 0 fields): this is not the same as "wrong." A large share of them are C++ types that genuinely compile to 1 byte by design — enum-only namespacing structs (e.g. struct ACTOR_AGGRO_RADIUS { enum { kWarn, kWarnAndAttack, kAttack }; };, which really is sizeof==1), RAII lock guards and utility classes with no data members. Of the full EMPTY bucket, only 6 classes have a header-provided static_assert proving the placeholder is actually wrong — down from 9, after patch 0031 fixed the shared root cause behind 3 of them (BSReadLockGuard/BSWriteLockGuard/BSSpinLockGuard each hold a single reference-type (T&) member; the parser had a branch to resolve a pointer-typed field but none for a reference-typed one, so the field silently dropped). The remaining 6 (AttachedScript, BGSNumericIDIndex, BSScrapArrayAllocator, GFxFunctionHandler::Params, GFxResourceLib::ResourceSlot, LogEvent) were checked and are a different, unrelated mechanism (or several) — not chased further this pass, per this project's own "two focused attempts, then defer" discipline. The other ~1,035 EMPTY entries have no static_assert to check against either way — genuinely unverified, not confirmed either correct or wrong. coverage_report.py's sweep output now prints these as two separate sections (EMPTY, CONFIRMED WRONG vs. EMPTY, UNVERIFIED) instead of one undifferentiated bucket, so this distinction is checkable in every future sweep, not just asserted here. See patches/0031.
  • The patch-0008 cluster (deferred; reopening needs a fresh lead, not a retry). isPolymorphic() is template-blind for a base class that's itself a class-template specialization (e.g. FxDelegateHandler : public GRefCountBase<FxDelegateHandler, ...>) — root-caused, not fixed. See patches/0008-isPolymorphic-investigation-DEFERRED.md.
  • 13 classes remain UNRESOLVED by design after patches 0026–0028 worked the bucket down from 27 (typedef-of-template-specialization reporting gap, a RUNTIME_DATA2 ground-truth name collision, and nested-type recursion bugs — all root-caused and fixed). The remaining 13 are members of uninstantiated class templates, which the inline-embed architecture never registers as independent types — traced structurally, not just labeled. See patches/0028.
  • Patch 0007 is superseded, not applied. Its original diagnosis (a TypePool first-registration-wins keying bug on synthetic template names) turned out to be stale — later patches reworked the mechanism entirely — but the coverage gap it was chasing (hkInplaceArray<T,N>, BSTObjectDictionary<...> as a base, etc.) is now closed by patch 0025 via a different, current root cause. 0007's own doc carries a superseded-by note; nothing from it is in the accepted patch set.

runtime-harness — live verification status

✓AIProcessInspector — confirmed live
✓SavegameTracer — confirmed live
?HavokStepLogger — silent, root cause unresolved
  • HavokStepLogger has produced zero log lines across 70+ minutes of real gameplay (Helgen opening, open-world Whiterun, combat). The vfunc index it hooks was hand-verified against the full inheritance chain and is very unlikely to be an indexing bug. Checked against real prior art (ersh1/Precision, the standard Havok-hooking reference in the SKSE community): it doesn't vtable-hook bhkCharacterState::Update at all — it hooks bhkWorld's physics-step function directly via an Xbyak mid-function trampoline. Current vtable hook: open question, not a known-good hook. Scoped follow-on (rebuild Precision-style) identified but not attempted. See runtime-harness/README.md (search "HavokStepLogger").
  • SavegameTracer can't read its own event payloads. BSSaveDataEvent and BGSSaveLoadManagerEvent are only ever forward-declared in the vendored tree, never defined — so the inspector dumps BGSSaveLoadManager::saveGameList (fully defined) instead, which is a real and useful substitute but not the event payload itself.
  • LayoutValidator's live checks cover only the classes it compiles in (11 hotspot classes plus the game-session checks: PlayerCharacter sanity, ACTOR_RUNTIME_DATA plausibility, an ExtraDataList walk, RTTI readback, and a vtable-pointer identity check — all verified against a real save load). It is a spot-check against the running game, not a full-archive live diff. See T3-3_LAYOUTVALIDATOR_REPORT.md.

Access blockers

  • IDA .til export execution (T1-4) is blocked on IDA access. The design and intermediate-JSON format are done and don't need it — only running the actual export against real IDA does. See TIL_EXPORT_DESIGN.md.
  • Publishing a real public GitHub Release is wired and dry-run-safe but has never been dispatched for real — it's a public action, gated on a human decision, not a technical blocker.
If a number on another page looks stale relative to this one, this page is not necessarily wrong — coverage numbers move as patches land. Check the linked patch docs and coverage_baseline*.json for the current state; this page tracks known categories of limitation, not a live number feed.
